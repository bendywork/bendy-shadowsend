### 2.2 UI 现状与问题清单（改版依据）

1. **设计令牌已有底子但未成体系**：`globals.css` 已定义 `--bg-base/panel/card`、圆角/阴影/聚焦环与 `.surface-card`/`.field`/`.btn-primary`/`.segmented`/`.icon-btn`/`.popover-panel`/`.tooltip-bubble`；但强调色仍是系统蓝（`#0a84ff` / `#0071e3`），与「黑白灰」不符（dc-02 已定：纯黑白灰 + 反色主按钮，见 §5）。
2. **浅色模式靠一串 `!important` 硬补**：`:root[data-theme="light"]` 下对 `.bg-black`/`.text-white`/`.bg-zinc-500/*`/`.border-zinc-500/*` 等逐类覆盖（9 组），脆弱、易漏。
3. **边框感重**：卡片、分段、弹窗、输入全带描边；聊天页仍有大量裸 zinc 工具类（历史遗留），层级靠边框而不是留白/背景分层表达。
4. **弹窗体系各自为政**：房间入口、二维码、公告编辑、公告阅读、图片查看器为 5 处手写模态（统一 `fixed inset-0` + 重遮罩 + 描边卡片）；没有 Drawer / Sheet / Toast / 确认对话框 / 骨架屏等体系件。
5. **硬编码中文残留**：弹窗与菜单（退出房间/创建房间/加入房间/房间二维码/配置公告/上传公告图片/公告预览/我知道了/关闭/房主转让/移除房间/成员操作）未接入 `t()`；`messages.ts` 现有 164 键（zh+en）只覆盖了外壳。
6. **交互粗糙**：踢人/转让/解散/退出用原生 `window.confirm`（4 处）；复制反馈、加载态、错误提示各写各的；无统一 toast。
7. **首页**：打字机标语 + 双径向光斑仍在，信息层级弱；身份卡信息少；表单校验提示弱。
8. **移动端**：靠 `order` 切换堆叠三栏，不是抽屉式导航；断点行为无成文规范（dc-04 已定：含移动端重构，手机/平板/桌面全适配，见 §5）。
9. **元信息过时**：`layout.tsx` 的 `<title>` 为 "Temp Bendy"、description 为英文 "Temporary encrypted chat app built with Next.js, PostgreSQL and S3."。
10. **巨石组件**：`src/app/room/[roomCode]/page.tsx` 已 2879 行（房间树/成员/公告/上传/弹窗全在一个文件），改版前需先拆分（ui-45）。

### 2.3 上传链路现状（痛点）

- **三条通道混杂**：`upload-url`（S3 预签名直传，120s）、`upload`（服务端中转：图片优先 DUFS、非图片有 S3 走 S3、否则 DUFS；名义上限 200MB）、`upload/chunk`（仅图片，DUFS append 分片 3MB）。另有 `OSS_PREVIEW_RPC_URL` 外部预览通道。
- **配置繁多**：`S3_*`（6 项）、`DUFS_*`（4 项）、`OSS_PREVIEW_*`（3 项），README 环境变量表 14 行——用户原话「配置项太多、太乱，很难去啃懂」。
- **生产瓶颈**：Vercel 函数请求体上限 4.5MB，`upload` 中转路径在生产实际只能承载 ≤4.5MB（超出直接 413），与「200MB 中转上限」的代码设定不符。
- 常量：`MAX_ATTACHMENT_SIZE_BYTES`=10GB（名义）、`MAX_PROXY_UPLOAD_BYTES`=200MB、`CHUNKED_UPLOAD_THRESHOLD_BYTES`=3MB。

### 2.4 关键平台约束（实测，影响方案选型）

- **Vercel**：函数请求体 / 响应体上限 4.5MB（非流式；**流式响应不受限**）。
- **Cloudflare Workers**：请求体上限 Free/Pro **100MB**、Business **200MB**（Enterprise 更大）；响应无硬性上限，支持流式转发（内存 128MB/isolate，需流式而非缓冲）。
- **浏览器直连第三方服务被 CORS 阻断**（实测见附录 A/B）；**服务端中转可行**（已实测上传成功）。
- **数据模型**：`MessageAttachment.storage` 为枚举（现仅 `S3` / `DUFS`），接入新通道需要一次最小迁移（见 §4.6）。

## 四、方向二：上传通道重构（12 条）

### 4.1 目标（引用需求原文拆解）

- 上传直连第三方资源：「图片 → `https://file.sang.pub/`；非图片类 → `https://pic.sl.al/`」。
- 「大文件就分片传，最后接收方合并」「小文件就直接传」「200 兆以内的非图片类就直接传」。
- 「尽量让老的配置配上去也不生效（兼容老的配置，但老的配置可有可无）」——旧 S3/DUFS/OSS 配置保留但不再参与新上传，配置项保持简单。

**决策结论（2026-10-13）**：dc-01 = B（仅 Vercel 分片，单请求 ≤4.5MB、≈4MB/片，不新建 CF Worker）；dc-05 = A（旧配置不再生效、仅维持存量读取）；dc-06 = A（明确报错 + 同服务有限重试 2-3 次）。

### 4.2 第三方服务实测（2026-10-13）

**file.sang.pub（图片）**

- 端点：`POST https://file.sang.pub/api/upload`；Header：`X-Upload-Type`（通道）、`X-File-Name`（encodeURIComponent）、`X-File-Size`（字节）；Body：原始文件。
- 通道：`meitu`（图片 .jpg/.jpeg/.png/.gif/.webp，≤20MB）→ 返回 `https://xiuxiu-pro-new.meitudata.com/posters/<hash>.png`；`icve`（除 .html/.htm，≤100MB）→ `https://file.icve.com.cn/file_doc/...`；另有 `waimai`（≤10MB）、`github`（≤10MB）备用。
- 响应：`{"code":200,"msg":"success","data":"<url>"}`；错误 `{"code":4xx,"msg":"..."}`。
- 服务端调用无需 Referer / 鉴权；实测图片与文件均上传成功、返回 URL 可公网直读。

**pic.sl.al（非图片）**

- 两段式：① `POST /api/upload-token`（Header 需 `Referer: https://pic.sl.al/`、`X-Requested-With: XMLHttpRequest`）→ `{"ok":true,"token":"<JWT>","expires_in":600}`，并下发 `__Host-imgsess` cookie；**token 与 UA 绑定**（JWT 内含 ua 哈希），换取与上传必须同一 UA。② `POST /api/upload`（Header：`X-Filename`、`X-Upload-Token`、`X-Requested-With`；Body 原始文件）→ `{"success":true,"data":{"url":"https://pic.sl.al/f/pic/YYYY-MM-DD/...","file_id":...}}`。
- 限额：单文件 ≤200MB；扩展名白名单（文档/压缩/音视频/图片等 60+ 类，拒绝可执行与活动脚本）；可重试状态码 `[408,409,429,500,502,503,504,520,522,524]`，支持 `Retry-After`。
- 实测服务端上传成功；跨域请求 403（ACAO 限定自有源）。

### 4.3 关键约束

- **CORS**：两服务均无法浏览器直连（`file.sang.pub` OPTIONS 404 无 CORS 头；`pic.sl.al` 跨域 403）→ 必须服务端中转。
- **中转层请求体上限与裁决**：Vercel 4.5MB 不够用；CF Workers Free/Pro 100MB、Business 200MB（未采用）。**dc-01 = B（已定）**：不新建 CF Worker，统一走 Vercel 分片——单请求 ≤4.5MB，所有超限文件按 ≈4MB/片分片（200MB ≈ 50 片），接收方合并。
- **下载侧**：第三方返回直链可公网直读，接收方下载不经我们的中转层（省流量与配额）。

### 4.4 架构与数据流（dc-01 = B 已定）

```
浏览器 ──(单请求 ≤4.5MB)──▶ Vercel 应用内服务端路由 ──▶ file.sang.pub / pic.sl.al
   │
   └──(超限)──▶ 前端分片（≈4MB/片）──▶ 逐片经服务端路由转发 ──▶ 服务侧多个分片文件
下载：第三方直链；分片：提供「合并下载」端点（按序流式拼接）供接收方一键保存
```

- 分片规则：单请求 ≤4.5MB；所有超限文件按 ≈4MB/片分片（服务限额内：sang ≤100MB、picsl ≤200MB；200MB ≈ 50 片）。图片通道选择（meitu ≤20MB / icve ≤100MB）不变。
- 无新增基础设施：不建 CF Worker / 网关，转发与分片编排均在 Vercel 应用内（见 up-03）。
- 体验与可靠性：分片并发上传 + 失败续传（up-11）缓解片数多的问题；接收端合并下载 + 完整性校验（up-10）兜底。

## 附录 A：file.sang.pub 实测记录（2026-10-13）

- `OPTIONS /api/upload` → 404（无 CORS 响应头）→ 浏览器直连不可行。
- 服务端 `POST /api/upload` + `X-Upload-Type: meitu`（图片 ≤20MB）→ `{"code":200,"msg":"success","data":"https://xiuxiu-pro-new.meitudata.com/posters/<hash>.png"}`，URL 公网直读 200。
- 服务端 `POST /api/upload` + `X-Upload-Type: icve`（非 html 文件 ≤100MB）→ `https://file.icve.com.cn/file_doc/...`。
- 错误示例：`X-Upload-Type` 非法 → `{"code":400,"msg":"类型错误或缺失 X-Upload-Type"}`。

## 附录 B：pic.sl.al 实测记录（2026-10-13）

- 跨域 `POST /api/upload` → 403（ACAO 限定自有源）→ 浏览器直连不可行。
- 服务端：`POST /api/upload-token`（带 Referer + X-Requested-With）→ `{"ok":true,"token":"<JWT>","expires_in":600}` + `__Host-imgsess` cookie（HttpOnly / SameSite=Strict / 2h）。
- `POST /api/upload`（X-Filename + X-Upload-Token）→ `{"success":true,"data":{"url":"https://pic.sl.al/f/pic/YYYY-MM-DD/fileid_<id>_<name>",...}}`。
- 限制：单文件 ≤200MB；扩展名白名单；可重试状态码 `[408,409,429,500,502,503,504,520,522,524]`；`Retry-After` 生效。
