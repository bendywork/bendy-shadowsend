# 文案规范（语气 / 长度 / 格式 / i18n）

> 适用版本：v0.1.69（REQ-202610-0499 / ui-36）
> 目标：空态、错误、提示、确认等界面文案使用同一套语气、长度与格式；所有可见文案通过 `t()` 引用，中英文键位与占位符严格对齐。

## 1. 适用范围

- 覆盖 `src/lib/i18n/messages.ts` 中全部 zh/en 文案：按钮、标签、空态、字段提示、Toast、错误、表单校验。
- 组件内不再新增硬编码可见文案；临时未迁移的页面文案按 ui-37 的清单继续收口。
- 聊天正文、用户昵称、后端返回的业务消息不属于本规范，保持原文。

## 2. 语气与用词

1. **平静、直接、可执行**：先说明发生了什么，再说明下一步；不责备用户。
2. **不卖萌、不玩梗**：不使用「呀、啦、哦」等语气词，不使用网络流行语。
3. **不用 emoji、不用感叹号**：状态由图标、颜色与文案共同表达，不靠符号堆叠情绪。
4. **统一人称**：面向用户时省略主语（「保存失败，请重试」），需要说明后果时用「你」（「退出后，你将无法继续查看房间内容」）。
5. **统一术语**：见 §9，不在同一界面混用同义词。

## 3. 长度预算

| 类型 | 中文上限 | 英文上限 | 说明 |
| --- | --- | --- | --- |
| 按钮 / 标签 / 菜单项 | 8 字 | 28 字符 | 动词开头；同一动作只用一个说法 |
| 字段提示 / 说明（`.hint`） | 40 字 | 90 字符 | 单句；不加句末标点 |
| 输入占位符（`.placeholder`） | 40 字 | 90 字符 | 描述输入内容或示例；不加句末标点 |
| Toast / 轻提示 | 32 字 | 80 字符 | 一句话；不加句末标点 |
| 表单校验 | 28 字 | 70 字符 | 指出字段与规则；不加句末标点 |
| 空态说明（`chat.empty`） | 30 字 | 70 字符 | 一句完整的话，可带句号 |
| 确认框标题 | 12 字 | 40 字符 | 简短问句，以「？」结尾 |
| 确认框描述 | 48 字 | 120 字符 | 说明对象、后果与不可逆性 |

超过预算时优先删修饰语，不缩字号、不换行堆叠。

## 4. 格式规则

### 4.1 标点

- 中文使用全角标点：`，。：；？！`；引号使用「」；省略号使用 `…`（U+2026），不用 `...`。
- 英文使用半角标点：`, . : ; ? !`；引号使用 “”；省略号使用 `…`。
- **标签、按钮、Toast、错误、表单校验不加句末标点**；空态说明与确认框描述使用完整句，中文以「。」结尾、英文以 `.` 结尾。
- 问句只在确认框标题、需要用户回答的场景使用「？」/ `?`；普通提示不使用反问句。

### 4.2 空格与数字

- 中文与阿拉伯数字之间留一个空格：「6 位数字」「最多 3 张图片」。
- 数字与单位之间按常见写法：`200MB`、`10 分钟`、`2 分钟`。
- 中英文混排时，英文单词与中文之间留一个空格（`Ctrl+V 粘贴`）。
- 不在中文文案中使用连续空格；分隔符统一用「/」并在两侧留空格（「加入 / 管理」）。

### 4.3 占位符

- 统一使用 `{name}`、`{count}`、`{max}`、`{code}` 等命名占位符；占位符内容不翻译。
- 同一键的中英文必须使用**同名、同数量**的占位符，顺序可不同。
- 占位符两侧按中文/英文语法自然留空格，不把标点粘在占位符上。

## 5. 空态文案

空态由「对象 + 下一步」组成，避免只写「暂无」：

| 场景 | 中文 | 英文 |
| --- | --- | --- |
| 聊天无消息 | 暂无消息，发送第一条消息开始对话。 | No messages yet. Send the first message to start the conversation. |
| 房间列表为空 | 暂无房间 | No rooms yet |
| 审批列表为空 | 暂无待审批申请 | No pending requests |

规则：

- 列表/分组空态可用短标签（「暂无房间」），不加句号。
- 聊天主区域空态用完整句，给出下一步动作。
- 空态不写「这里什么都没有」这类无信息文案，也不使用插画替代说明。

## 6. 错误文案

错误文案分三层，展示层规则见 `docs/design-system-feedback.md`：

1. **网络异常**：统一「网络异常，请检查网络后重试」/ `Network error, check your connection and try again`，不暴露 URL、HTTP 方法或浏览器内部错误。
2. **业务错误（4xx）**：保留后端可读消息；后端消息本身不符合本规范时，由前端兜底文案接管。
3. **服务端 / 解析错误**：使用调用方传入的本地化兜底文案，不展示堆栈、状态码或解析细节。

句式：

- 可重试：`<动作>失败，请重试` / `Failed to <action>, please retry`。
- 有明确原因：`<动作>失败：<原因>` / `Failed to <action>: <reason>`。
- 需要用户操作：`无法<动作>，请<下一步>` / `Could not <action>, <next step>`。
- 表单校验：`请输入<字段>`、`<字段>必须是 <规则>`、`<字段>不能超过 {max} 个字符`；不写「错误」「非法」等笼统词。

禁止：

- 「操作失败」「出错了」「未知错误」这类没有下一步的文案。
- 把 `error.message`、HTTP 状态码、接口路径直接展示给用户。
- 同一次失败同时弹 Toast 和行内错误（字段级错误只走行内）。

## 7. 提示 / Toast 文案

| 类型 | 句式 | 示例 |
| --- | --- | --- |
| 成功 | `已<动作>` / `<对象>已<动作>` | 已复制、房间名称已更新、加入链接已复制 |
| 进行中 | `正在<动作>…` / `<动作>中…` | 解散中…、保存中… |
| 中性信息 | 陈述结果 + 可选下一步 | 已提交加入申请，等待房主审批 |
| 警告 | 说明限制 + 下一步 | 单次最多发送 {max} 个文件 |
| 错误 | 见 §6 | 创建房间失败，请重试 |

- Toast 不加句末标点，长度不超过 32 字（英文 80 字符）。
- 成功提示不重复按钮上已经表达的结果；纯图标按钮需要 Toast 补足结果（见复制反馈规范）。
- 同一错误由 Toast store 去重，不在调用方重复弹。

## 8. 确认与危险操作文案

- 标题：简短问句，以「？」结尾，如「移除成员？」「解散房间？」。
- 描述：说明对象、后果与不可逆性；对象名用「」包裹，如「将「{name}」移出房间后，对方将立即失去访问权限。」。
- 按钮：使用具体动词短语（「移出房间」「转让房主」「退出房间」「解散房间」），不用「确定」「是」「否」。
- 进行中：`正在<动作>…`，并禁用所有关闭路径。
- 英文标题同样使用问句，描述使用完整句并以 `.` 结尾。

## 9. 术语表

| 概念 | 中文 | 英文 | 说明 |
| --- | --- | --- | --- |
| 房间 | 房间 | room | 不写「聊天室」「群组」 |
| 房间号 | 房间号 | room code | URL 中的随机码 |
| 门禁码 | 门禁码 | gate code | 6 位数字，不写「密码」「邀请码」 |
| 邀请链接 | 邀请链接 | invite link | 一次性 token，不写「二维码链接」 |
| 公告 | 公告 | announcement | 不写「通知」「消息」 |
| 成员 | 成员 | member | 房主也是成员；「房主」单独称呼 |
| 房主 | 房主 | owner | 不写「管理员」「群主」 |
| 解散房间 | 解散房间 | dissolve room | 不写「删除房间」「关闭房间」 |
| 移出成员 | 移出成员 | remove member | 不写「踢人」作为界面文案 |

## 10. i18n 对齐

- 所有界面文案写在 `src/lib/i18n/messages.ts` 的 `zh` / `en` 两张表中，通过 `t("key")` 引用。
- 键名使用「模块.对象.动作/状态」：`toast.copyFailed`、`settings.gateCode.placeholder`、`chat.empty`。
- 中英文键位由 `MessageKey` 在编译期强制对齐；占位符由 `src/lib/copywriting.ts` 的审计函数在测试期校验。
- 新增键必须同时补 zh/en；不允许只写中文再用英文兜底。
- 语言切换后同一状态文案语义一致，不出现中文键值残留英文标点、英文键值残留全角标点。

## 11. 可执行校验

实现：`src/lib/copywriting.ts`，测试：`src/lib/copywriting.test.ts`。

审计规则：

- zh/en 键位与占位符对齐；
- 无 emoji、无首尾空格、无连续空格；
- 中文无半角句读标点、英文无全角标点、无 `...`；
- Toast / 占位符 / 提示不加句末标点，空态说明按类型处理；
- 错误文案包含「请 / 检查 / 重试 / ：」等可执行信息；
- 按 §3 的长度预算检查。

`npm test` 会在文案表改动后自动执行上述审计。

## 12. 验收清单

- [ ] 空态、错误、提示、确认文案均符合 §5–§8 的句式。
- [ ] 中文标点全角、英文标点半角，数字与中文之间留空格。
- [ ] 所有新增文案均有 zh/en 两份，占位符同名同数量。
- [ ] Toast 与错误文案不超过长度预算，且包含下一步动作。
- [ ] 术语表内的概念在全站使用同一说法。
- [ ] `npm test` 中 `copywriting` 审计为 0 条问题。
